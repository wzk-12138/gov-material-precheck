## 1 项目背景

云州市便民服务中心「办事材料预检与服务协同」现状为纯人工链路：线上清单与窗口实际要求不一致，群众按线上清单备齐材料后仍被窗口退回补正，形成「材料补了一次又一次」的反复跑。现场调研与业务挖掘材料给出的可核对口径为：补正率约 36%、清单解释约 12 分钟/次、每日约 600 件咨询、人工逐项核对约 8 人时/日；同时存在三套「办完」口径、便签说明不随单据交接、规则版本冲突、关键系统不可用等协同问题。

上述数字均为访谈口径，样本与时间窗待复核，本系统不作为已验证基线使用，只作为需求背景。现状流程图见同目录 `云州市便民服务中心-现状流程图.png`。

## 2 系统定位与边界

系统定位为**只读核对 + 人工交接的辅助智能体**，只做两件事：清单一致性预检、补正解释提示。

明确不做：

- 不输出批准结论、不判断能否受理、不解释真实法律效力；
- 不代替行政审批，不回写任何业务系统；
- 不导入真实个人材料，不使用云端模型或外部数据服务；
- AI 结论一律不直接生效，必须挂人工确认单，由接手岗位确认后才完成责任转移。

首期范围：两类非紧急事项、历史资料回放后小范围并行试点；一致率 99% 属验收目标，基准与裁定人待定，不在代码中写死。

### 3.2 非功能与代码约束

- 所有对外接口统一返回 `{"ok": bool, "data": ..., "error": {"code": str, "msg": str}}`；业务失败也返回 HTTP 200，由 `ok` 与 `error.code` 判定。
- 配置文件统一为 `config.yaml`；密钥、模型地址、模型名、端口、阈值、红线词表一律不写死在代码中。
- 每个函数写中文 docstring，说明入参、出参、失败时的行为；关键业务逻辑（安全审查、权限校验、人工确认、认证）写中文行内注释说明「为什么这么卡」；源码每行带注释。
- 不引入需求之外的框架或中间件：无数据库、无向量库、无图数据库、无消息队列、无缓存、无第三方 Agent 框架、无模型 SDK。
- RAG 只做「检索 → 增强 → 生成」三段，不接 embedding 服务、向量库或外部知识 API：检索仍用标准库 IDF 余弦加图谱关联扩展，换资料只需重建 `kb/rules.json`。
- LLM Wiki 条目由本机模型起草，但**起草不等于发布**：未过人工确认的条目只对管理员可见，不进 RAG 语料，避免模型自写自用把错误口径固化进知识库。
- 管理员（SaaS）与业务岗职责分离：能改权限、改分层、发规则版本的人，默认不能发起预检、不能签核业务结论。

> 关于 ②：任务书只给出 `harness` 一词。经核对同名 PyPI / GitHub 包要么为空壳、要么依赖云端 provider 与 Redis / Modal，与「本地部署、不引入未点名中间件」冲突，因此实现为项目内自研运行壳 `AgentHarness`。若课程指定的是某个具体仓库，只需替换 `app/harness.py` 的接入层，其余模块不变。

> 关于 ④：白板把权限拆成「管理员（SaaS）」与「用户（分层）」两支。管理员管平台与账号，不管业务结论；用户按层级决定能看多少原文、能否给结论、能否签核。两支都由 `app/permissions.py` 判定，租户与层级写在令牌里，请求体不参与鉴权，避免改个字段就换身份。

## 4 总体架构

分层如下，全部进程内调用，无跨服务通信：

```
对外接口层   app/main.py        FastAPI 路由、参数校验、统一响应、全局异常、认证依赖
运行壳层     app/harness.py     AgentHarness 八步编排（唯一业务入口）
关卡层       app/guards.py      安全审查 / 权限校验 / 输出审查
             app/auth.py        角色令牌绑定认证（租户 + 角色 + 层级）
             app/confirmation.py 待确认单与签核
             app/permissions.py  管理员（SaaS）/ 用户分层判定、租户隔离   ← 白板 ④
RAG 层       app/rag.py         RAG 三段编排：检索 → 增强 → 生成        ← 白板 ③
能力层       app/knowledge.py   规则库构建与标准库检索
             app/graph.py       知识图谱构建、关联查询、多跳推理、原子落盘
             app/wiki.py        LLM Wiki 条目生成、人工确认后发布        ← 白板 ③
             app/llm.py         本机 Ollama 调用与降级
基础层       app/common.py      配置加载、统一响应、JSON / JSONL 本地存储
数据层       kb/rules.json      36 条合成事实（规则库）
             kb/graph.json      知识图谱快照（节点 + 语义关联）
             kb/wiki.json       Wiki 条目快照（draft / published + 版本）   ← 白板 ③
             data/*.json(l)     待确认单、业务审计、管理员审计流水
配置层       config.yaml        唯一配置入口
```

一次预检的数据流：

```
请求（X-Role / X-Actor / X-Agent-Token + 业务编号 / 问题 / 材料名）
  → 认证依赖 _gate（令牌同源；租户与层级只从令牌取，不读请求体）
  → ① 权限校验 check_role + check_tier（管理员不得发起预检，越层即拒）
  → ② 安全审查 review_input
  → ③ RAG 检索 knowledge.search（IDF 加权余弦，取 top_k 证据）
  → ④ RAG 增强 graph.evidence_chain（沿事实↔事实关联多跳扩展）+ wiki 条目摘要
  → ⑤ 取版本 rule_version + wiki_version
  → ⑥ 组装提示词 → 本机 Ollama /api/chat（未就绪则降级）
  → ⑦ 输出审查 review_output（越权结论脱敏）→ ⑧ 生成待确认单 + 写审计
  → 统一响应：建议 + 证据 + 关联链 + 条目摘要 + 待确认单 + 模型状态（requires_human_confirmation 恒为 True）
```

## 5 八步编排与三道卡点

| 步骤 | 动作 | 拦截原因（为什么这么卡） |
| --- | --- | --- |
| 1 | 权限校验（角色 + 分层 + 租户） | 只有授权岗位能发起预检；无角色、伪造角色、越层、跨租户、管理员走业务接口，一律拒绝，防止改个请求头就换身份 |
| 2 | 输入安全审查 | 真实个人材料、超长文本、要求系统作行政审批或解释法律效力的说法，全部拦在检索之前且不落盘原文 |
| 3 | RAG 检索 | 只用合成资料与已发布 Wiki 条目；无命中即「无依据」，不调模型、不凭空生成 |
| 4 | RAG 增强（图谱证据链 + 条目摘要） | 从命中事实沿知识关联扩展到关联事实，并补一条 Wiki 条目摘要，让每条提示可回溯到证据链 |
| 5 | 资料与条目版本 | `rule_version` 与 `wiki_version` 同时写入待确认单与审计，便于事后定位用的是哪一版规则、哪一版条目 |
| 6 | RAG 生成（本机推理） | 仅当存在依据才调模型；按角色与分层决定给模型看原文、条目摘要还是仅标题 |
| 7 | 输出安全审查 | 模型可能被提示注入诱导输出批准 / 受理 / 效力结论，命中即脱敏并强制转人工 |
| 8 | 人工确认 + 审计 | AI 只作提示，任何建议必须挂单据；接手人、确认时间、人工改动、签核人入审计才能重建处理链 |

人工确认门细化：禁止发起人自确认、单据 3600 秒超时作废、结论白名单 `accept / reject / revise`；写知识关联还额外要求单据已 `confirmed`、登记人必须是该单据签核人、业务编号一致、关系语义在白名单内、三元组不重复。

## 6 知识库设计（一）：规则库与 RAG 链路

白板的「知识库」由两层构成：本节的规则库 + RAG 链路负责**怎么取、怎么给模型看**；§7 的知识图谱与 LLM Wiki 负责**知识之间怎么连、怎么读**。两层共用同一套事实编号。

### 6.1 规则源与规则库

- **规则源**：仅 `../discovery-report.json` 的 `requirements[].evidence[]`，取 `id / text / source / character` 与需求标题，构建时按证据编号去重；命中身份证号、手机号等个人材料特征的条目只计数不入库（本次 `skipped=0`）。
- **规则库**：`kb/rules.json`，含 `rule_version`（源资料 `generatedAt`）、`count=36`、逐条 `id / short_id(f00–f55 形式) / topic / text / source / character`。
- **检索算法**：纯标准库实现。中文按单字 + 相邻二字切分，英文数字成词；词频经平滑 IDF 加权后计算余弦相关度；`min_score=0.02` 以下视为无依据，`top_k=3`。不依赖分词库或向量库，代价是长问句命中可能偏，需按资料调阈值。
- **权限脱敏**：`can_view_material=false` 的角色（热线、平台、主任）只拿到编号与标题，连提示词里都不塞原文；分层低于 L2 的用户同样只看编号与标题。

### 6.2 RAG 三段链路

RAG（Retrieval-Augmented Generation）在本方案里不是一件新中间件，而是一条固定的三段编排，落在 `app/rag.py::build_context`，由 `AgentHarness` 第三步到第六步调用：

| 段 | 输入 | 动作 | 输出 | 硬约束 |
| --- | --- | --- | --- | --- |
| Retrieve 检索 | 咨询问题 + 已提交材料名 | `knowledge.search` 取 `top_k=3` 命中事实 | 带 `short_id` 的证据列表 | `min_score` 以下不进上下文；无命中直接走兜底，不调模型 |
| Augment 增强 | 命中事实 + 角色分层 | `graph.evidence_chain` 取 2 跳关联（≤24 跳）+ `wiki` 条目摘要 + 按 `can_view_material` 裁剪正文 | 固定格式的上下文块 | 只放 ≤3 条证据、≤8 个关联编号、≤1 条条目摘要；编号必须与检索结果一一对应 |
| Generate 生成 | 系统提示词 + 拼好的上下文 | 本机 Ollama `/api/chat`（`temperature=0.1`、`num_predict=160`、`think=false`） | 引用编号的建议文本 | 必须引用给定编号；模型未就绪按 `required=false` 降级，不阻塞人工流程 |

> 为什么把上下文压这么小：`qwen3.5:0.8b` 在长上下文里最容易编造编号（§16 风险 9），实测把证据压到 3 条、关联只给编号后，`precheck` 约 6 s 出可用建议。RAG 的目标不是「把资料全塞进去」，而是「每条结论都能指回一条编号」。这也是全流程不用向量库的原因：535 条关联的规模下，图谱 2 跳扩展 + IDF 余弦已经够用，多一个向量库就多一份无法核对的黑盒。

## 7 知识库设计（二）：知识图谱与 LLM Wiki

### 7.1 节点与关联

| 类型 | 数量 | 说明 |
| --- | --- | --- |
| fact 事实 | 36 | 每条规则事实一个节点，正文放 `meta.text` 便于按权限裁剪 |
| topic 需求 | 6 | 需求标题 |
| role 岗位 | 6 | 访谈事实提出岗位 |
| source 资料 | 6 | 由 `source` 串末段提取的資料类型 |
| version 版本 | 1 | 当前资料版本 |

合计 **55 节点 / 535 条关联 / 11 类关系**。关联均为可核对依据，未编造冲突关系：

| 关系 | 条数 | 建边依据 |
| --- | --- | --- |
| 属于需求 / 包含事实 | 36 / 36 | 事实归属 `requirements` 分组及反向 |
| 由谁提出 / 涉及岗位 | 36 / 36 | `evidence.character` 及反向 |
| 出自资料 / 收录事实 | 36 / 36 | `evidence.source` 及反向 |
| 生效版本 / 版本收录 | 36 / 36 | 规则库版本及反向 |
| 同一需求共现 | 180 | 同需求内事实两两组合，正反向各一条 |
| 内容相关 | 54 | 正文中文二字词 Jaccard ≥ 0.08，每条事实最多 3 条，取相关度最高者，`note` 写明分值 |
| 援引 | 13 | 事实正文完整包含另一事实原文，直接援引关系 |

### 7.2 查询能力

| 能力 | 算法 | 关键参数 |
| --- | --- | --- |
| 关联查询 `relations` | 扫描关联表，出向 + 入向，按 `rel` 过滤 | `max_nodes=60` |
| 最短关联链 `shortest_path` | 广度优先 + 父指针回溯 | 只走事实↔事实关联 |
| 多跳子图 `subgraph` | 逐层 BFS，节点附跳数 | `max_depth=4`、`max_nodes=60`、`max_edges=120` |
| 证据链 `evidence_chain` | 多源 BFS，逐跳去重并按 (跳数, 关系) 排序 | `evidence_depth=2`、`max_hops=24` |
| 人工写关联 `add_link` | 三元组去重后原子落盘，重启自动回载 | `writable_relations` 六种白名单 |

> 早期版本允许沿全部双向边扩散，2 跳即覆盖全图（340 跳），证据链失去可核对性。现限定「只沿事实↔事实的关联扩散」并加条数上限，超限时返回 `truncated=true`，不得把截断结果当完整图。

### 7.3 LLM Wiki（知识图谱的可读面）

图谱对人是不可读的：55 个节点、535 条边，窗口人员没法照着边列表向群众解释。LLM Wiki 就是把图谱渲染成「条目」的只读阅读层，也是 RAG 的语料层——检索命中的事实，可以带一条人话摘要一起进提示词。

| 要素 | 设计 |
| --- | --- |
| 条目粒度 | 一个图谱节点一条 Wiki 条目（事实 36 / 需求 6 / 岗位 6 / 资料 6 / 版本 1），条目 ID 与节点 ID 相同（如 `f10`） |
| 条目结构 | 标题、正文摘要（≤120 字）、关联条目列表（按其关系语义分组）、引用编号、状态、版本 |
| 起草 | 本机模型只依据该节点 `text` 与 1 跳关联起草摘要，`think=false`、`temperature=0.1`；不得引入节点外事实，不得输出结论性表述 |
| 发布门 | 起草结果状态 `draft`，**不进 RAG 语料、只对管理员可见**；必须由 L2 及以上签核人确认后转 `published`，才能被检索命中 |
| 版本 | `kb/wiki.json` 记 `wiki_version`、条目 `id / status / drafter / signer / refs / text`；重建图谱后条目重新起草，旧版本留档不覆盖 |
| 边界 | 不引入维基引擎或站点服务，只有本地 JSON + 只读页面；条目不自动外发、不回写业务系统 |

> 为什么不做「模型自动写 Wiki」：模型自己写、自己检索、自己引用，等于把没人核对过的说法固化成规则源。所以条目必须先由人签核（复用 §5 第 8 步的待确认单），签核人、起草人、引用编号都进审计；`draft` 状态对业务岗不可见，避免未核实的摘要被当成口径。

## 8 本地模型接入（Ollama）

- 调用方式：标准库 `urllib.request` POST `http://127.0.0.1:11434/api/chat`，请求体 `model / stream:false / think:false / options.temperature / options.num_predict / messages`；解析 `message.content`。地址、模型名、超时、温度、生成上限与思考开关全部来自 `config.yaml`。
- 参数：本机已拉取 `qwen3.5:0.8b`（约 1 GB、CPU 推理）、`temperature=0.1`、`max_tokens=160`、`think=false`、`timeout_seconds=30`、`probe_timeout_seconds=5`。低温度减少自由发挥导致的越权结论。
- 实测修正：`qwen3.5` 属思考型模型，默认开启 thinking 时结果落在 `message.thinking`、`content` 为空，且没有生成上限时 CPU 连续输出 2509 token 仍未停止；因此请求显式关闭思考并设 `num_predict`，系统提示词追加「回答控制在 120 字内」。实测真实推理 `llm.generate` 约 1.7 s、完整 `precheck` 约 6 s，返回可用建议且 `degraded=false`。模型返回空正文时主动降级，不把空建议算作推理成功。
- 降级：`required=false` 时连接拒绝 / 超时 / HTTP 错误均返回 `degraded=true` 且 `text=""`，上层改用检索提示兜底，人工确认链路照常；`required=true` 时抛 `OLLAMA_UNAVAILABLE`。响应结构异常抛 `OLLAMA_BAD_RESPONSE`；模型返回空正文同样按降级处理。
- 自检：`scripts/check_ollama.py` 用独立的 `probe_timeout_seconds` 探测 `/api/tags`，退出码 0 就绪 / 1 服务未启动 / 2 在线但缺模型，只打印可操作命令，不自动下载模型。服务在线且模型匹配时，`verify_stage3.py` 的 H10 自动断言真实推理未降级并产出非空建议。
- 数据不出本机：服务绑定 `127.0.0.1`，提示词中不含请求原文之外的业务数据，非授权岗位连证据原文都不进入提示词。

## 9 提示词设计

提示词完整设计、模板、变量来源、红线词表、示例与版本管理见 **`docs/技术方案提示词.md`**。核心约定：系统提示词集中在 `config.yaml` 的 `agent.system_prompt`；用户提示词由 `AgentHarness.precheck` 第六步按固定格式拼接，只注入业务编号、咨询问题、已提交材料名、检索证据（按权限与分层裁剪）、图谱关联编号与至多 1 条已发布 Wiki 条目摘要；输出必须引用证据编号，且必须再过一次输出安全审查。提示词里不出现租户 ID、令牌、管理员身份与 `draft` 条目。

## 10 安全、权限与数据红线

### 10.1 认证

`app/auth.py` 从环境变量 `AGENT_ROLE_TOKENS` 读取 `{"租户ID/角色键":"令牌"}` JSON（每次请求重读，支持运行时轮换），用 `hmac.compare_digest` 做常量时间比较；校验租户是否存在、角色是否在白名单、令牌是否签发、令牌归属角色是否与请求角色一致、层级是否达到该动作要求。错误码 `AUTH_NOT_CONFIGURED / AUTH_BAD_TOKENS / AUTH_TOKEN_DUPLICATED / AUTH_REQUIRED / AUTH_FAILED / AUTH_ROLE_MISMATCH / ROLE_REQUIRED / ROLE_UNKNOWN`。16 个业务路由统一挂 `Depends(_gate)`，`/health` 免凭据便于探活。凭据不落盘、不写进命令历史。

### 10.2 权限主体：管理员（SaaS）与用户（分层）

白板把权限分成两支，两支的判定都写在 `app/permissions.py`，令牌里带 `tenant / role / tier`，请求体不参与鉴权。

| 支 | 身份 | 能做什么 | 明确不能做什么 |
| --- | --- | --- | --- |
| 管理员（SaaS） | `platform_admin` 平台管理员 | 租户开通 / 停用、配额、全局审计导出、模型与规则版本发布 | 不能发起预检、不能签核业务结论、不能读取租户材料原文 |
| 管理员（SaaS） | `tenant_admin` 租户管理员 | 本中心账号开通 / 停用、授予与调整用户分层、凭据轮换 | 同上；且不能改自己的分层、不能单人关闭租户 |
| 用户（分层） | L1 / L2 / L3 三层业务用户 | 按层级使用预检、确认、签核、写关联等能力 | 越层动作一律拒绝；不能改自己的层级 |

职责分离的三条硬规矩：

1. **能改权限的人不出结论**：管理员调用业务接口返回 `ADMIN_FORBIDDEN_BIZ`；业务岗调用管理接口返回 `ADMIN_REQUIRED`。
2. **管理员动作单独留痕**：写入 `data/admin_audit.jsonl`，字段含操作人、租户、动作、前后值、时间；与业务审计分开，便于分别复核。
3. **敏感管理动作双人复核**：关闭租户、批量改分层、发布规则版本需要第二位管理员确认，单人提交只落 `pending`。

### 10.3 用户分层与角色矩阵

层级决定「能看多少原文、能否给结论、能否签核」，角色决定「在哪个岗位使用系统」：

| 层级 | 角色键 | 岗位 | 预检 | 查看材料原文 | 人工确认 | 分层附加能力 |
| --- | --- | --- | --- | --- | --- | --- |
| L1 一线执行 | `window` | 窗口工作人员 | 是 | 是 | 否 | 只能提交待确认单，不能签核 |
| L1 一线执行 | `hotline` | 热线服务负责人 | 是 | 否 | 否 | 只看到编号、标题与已发布条目摘要 |
| L2 业务复核 | `reviewer` | 业务审核员 | 是 | 是 | 是 | 可签核 `accept / reject / revise`，可签核 Wiki 条目 |
| L3 监督决策 | `supervisor` | 数据与流程监督员 | 是 | 是 | 是 | 可写知识关联 `/graph/link`、可查看全部审计回放 |
| L3 监督决策 | `director` | 服务中心主任 | 否 | 否 | 否 | 只读全部审计与指标，审批规则版本发布 |
| 管理员 | `tenant_admin` | 租户管理员 | 否 | 否 | 否 | 账号与分层管理、凭据轮换 |
| 管理员 | `platform_admin` | 平台管理员 | 否 | 否 | 否 | 租户开停、规则与模型版本发布、全局审计导出 |
| 管理员（技术） | `platform` | 政务平台工程师 | 否 | 否 | 否 | 只读运行日志、接口与快照维护、数据质量报告；不改分层、不签核、不发起预检 |

租户与分层判定规则：

- `tenant_id` 只从令牌派生；请求体或查询串里出现 `tenant_id` 直接 `TENANT_IN_BODY` 拒绝，防止改字段换租户。
- 令牌租户与资源租户不一致返回 `TENANT_MISMATCH`；`/wiki`、`/graph`、`/audit` 全部按租户过滤，跨租户查询不返回空结果而是报错，避免误以为「没有数据」。
- 层级不足返回 `TIER_INSUFFICIENT`；管理员缺业务角色返回 `ADMIN_FORBIDDEN_BIZ`；业务岗越权调用管理接口返回 `ADMIN_REQUIRED`。
- 层级与角色绑定写在 `config.yaml` 的 `permissions` 节，不在代码里写死；改层级必须走管理员动作并留审计。

### 10.4 数据红线

- 规则源仅合成训练资料；输入命中身份证 / 手机号等特征或超 600 字直接拒绝且不落盘原文。
- 禁止输入词：请批准、准予、直接审批、作出行政决定、是否具有法律效力。
- 禁止输出词：批准通过、准予受理、审批通过、具有法律效力、可以正式受理；命中即替换为脱敏提示并强制转人工。
- 审计保留业务编号、资料版本、事实引用、图谱关联、建议结果、人工改动、签核人；单行 JSONL 追加，可按业务编号回放重建处理链。

## 12 配置管理

`config.yaml` 为唯一配置入口，含 `service / auth / agent / ollama / knowledge / rag / wiki / permissions / roles / redlines / confirmation / audit / graph` 十三节。`load_config()` 用 `yaml.safe_load` 读取并校验必需节，缺节即抛 `CONFIG_INVALID`，绝不用代码内默认值补位；相对路径统一由 `resolve_path()` 挂到项目根目录。密钥（凭据表）走环境变量名 `AGENT_ROLE_TOKENS` 与 `AGENT_ADMIN_TOKENS`，模型地址与名称走 `ollama` 节，分层与角色绑定走 `permissions` 节（`tiers` / `role_tier` / `admin_roles`），RAG 参数走 `rag` 节（`top_k` / `min_score` / `evidence_depth` / `max_hops` / `wiki_summary_in_context`），Wiki 策略走 `wiki` 节（`draft_visible_roles` / `publish_min_tier` / `max_summary_chars`），均不出现在源码中。

## 16 已知风险与后续改进

1. **Ollama 服务需在新终端启动**（`ollama serve`）：模型权重 `qwen3.5:0.8b` 本机已拉取，代码不自动下载；服务在线时 `verify_all.py` 自动断言真实推理，离线时只覆盖降级路径并由本地假 Ollama 覆盖协议对接。会话关闭后服务可能退出，重跑验证前先启动。
2. **认证只在 HTTP 依赖层**：进程内直接调用 `AgentHarness` 仍免认证；凭据无过期、无轮换审计，`auth.required=false` 会退回明文模式。
3. **图谱快照优先回载**：改动 `discovery-report.json` 后必须重跑 `build_kb.py` + `build_graph.py`，否则关联仍是旧版本。
4. **业务失败也返回 HTTP 200**：调用方必须判断 `ok` 与 `error.code`，只看状态码会误判。
5. **本地 JSONL 审计**：写锁仅进程内有效，无留存期清理；多进程部署需换成带跨进程锁的存储。
6. **标准库中文检索**：`min_score / top_k / related_threshold / related_top_k` 为经验值，换资料后需重新校准。
7. **模型协议**：按 Ollama `/api/chat` 的 `message.content` 解析；若改用其他本地模型服务，只需改 `app/llm.py` 的解析分支。
8. **harness 释义**：按项目内自研运行壳实现；若课程指定具体仓库，替换接入层即可。
9. **小模型证据编号漂移**：0.8B 本地模型可能引用提示词未给出的证据编号；建议仅为提示，必须由接手人按返回的 `evidence_ids` 逐项核对后才生效，系统不自动采信。
10. **docx 由 md 转换生成**：改 `技术方案.md` 后需重建 `技术方案.docx`，`verify_docs.py` 的 D04 / D06 会在内容漂移时报错。
11. **Wiki 起草失真**：0.8B 模型写摘要时可能把两条事实揉成一条，或给出节点外结论。现在 `draft` 不进语料、业务岗不可见，只能靠 L2 及以上逐条签核兜住；条目多了以后签核本身会成为工时负担，需要抽样复核策略（尚未设计）。
12. **管理员权限过大**：`platform_admin` 能改租户、发规则版本，等于能改「系统认为对的东西」。现只做了职责分离（不能出业务结论）与双人复核（关租户、批量改分层、发版本），没有做到最小权限细分与定期权限复核，属后续要补的治理缺口。
13. **分层配置漂移**：层级与角色绑定写在 `config.yaml`，换人、借调、临时顶班时容易改配置了事，审计里只留管理员动作，不留「为什么改」。建议把分层变更也纳入 `data/admin_audit.jsonl` 的原因字段并定期比对组织花名册。
14. **RAG 上下文过窄**：只放 3 条证据、8 个关联编号是为了压住 0.8B 的编号漂移，代价是长问句、跨需求的问题可能「检索不到就不会答」。换更大模型后可上调 `rag.top_k`，但必须同步重跑 `verify_stage4.py` 的编号可回溯断言。
