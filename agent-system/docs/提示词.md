# 办事材料预检智能体 · 提示词设计

| 项目 | 内容 |
| --- | --- |
| 适用版本 | v1.0（对应 `docs/技术方案.md`） |
| 配置位置 | `config.yaml` → `agent.system_prompt` / `agent.no_evidence_hint` / `ollama.*` |
| 组装位置 | `app/harness.py::AgentHarness.precheck` 第六步 |
| 调用位置 | `app/llm.py::generate`（本机 Ollama `/api/chat`） |
| 规则源 | 仅合成训练资料 `kb/rules.json`，不含任何真实个人材料 |

---

## 1 设计原则

1. **不越权**：系统提示词第一句就限定「只做清单预检与补正解释提示」，明令不得输出批准结论、不得解释法律效力、不得承诺办理结果。
2. **可核对**：要求模型必须引用给定证据编号，用户提示词只提供本地规则库命中的事实编号与文本，不提供模型自由检索能力。
3. **最小必要**：只注入业务编号、咨询问题、材料名、检索证据、图谱关联编号；不注入账号、令牌、配置、审计流水、个体材料。
4. **权限脱敏**：`can_view_material=false` 的角色，证据位置只放 `topic` 标题，不放 `text` 正文——原文连提示词都进不去。
5. **配置外置**：系统提示词、兜底提示、模型名、温度、超时、生成上限与思考开关全部写在 `config.yaml`，代码不写死任何一句提示词。
6. **双层防御**：提示词约束之外还有输出安全审查；模型输出命中禁止词即脱敏并强制转人工，不依赖模型自觉。

## 2 系统提示词（逐字引用 `config.yaml`）

```
你只做办事材料清单预检与补正解释提示；必须引用给定证据编号；不得输出批准结论、不得解释法律效力、不得承诺办理结果；结论只作为待人工确认的建议；回答控制在 120 字内。
```

约束拆解：

| 子句 | 对应红线 | 失效时的兜底 |
| --- | --- | --- |
| 只做清单预检与补正解释提示 | 系统定位边界 | 输入审查 `APPROVAL_REQUEST_BLOCKED` |
| 必须引用给定证据编号 | 结论可回溯 | 无检索命中时不调模型 |
| 不得输出批准结论 / 解释法律效力 / 承诺办理结果 | 不替代行政审批 | 输出审查 `forbidden_output_words` 脱敏 |
| 结论只作为待人工确认的建议 | AI 结论不直接生效 | `requires_human_confirmation` 恒为 True |
| 回答控制在 120 字内 | 压住 CPU 推理耗时、避免生成上限截断 | 提示词约束 + `max_tokens=160` 双保险 |

## 3 用户提示词模板（逐字引用 `app/harness.py` 拼接格式）

```
业务编号：{business_id}
咨询问题：{question}
已提交材料：{materials_joined}
可引用规则：
[{short_id}] {text_or_topic}
[{short_id}] {text_or_topic}
...
关联事实编号（由知识图谱扩展）：{graph_refs_joined}
```

实际拼装代码（每行带注释，与源码一致）：

```python
context = "\n".join(f"[{h['short_id']}] {h['text'] if can_view else h['topic']}" for h in hits)  # 按权限决定给模型看原文还是仅标题
context += f"\n关联事实编号（由知识图谱扩展）：{'、'.join(graph_chain['related'][:8]) or '（无）'}"  # 只把关联编号交给模型，不塞关联节点原文
user_prompt = f"业务编号：{business_id}\n咨询问题：{question}\n已提交材料：{'、'.join(mats) or '（无）'}\n可引用规则：\n{context}"  # 组装用户提示
gen = llm.generate(self.cfg, str(self.cfg["agent"]["system_prompt"]), user_prompt)  # 调用本机 Ollama
```

## 4 变量来源与取值规则

| 变量 | 来源 | 规则 |
| --- | --- | --- |
| `{business_id}` | `POST /precheck` 请求体 | 必填，用于投诉关联与审计重建 |
| `{question}` | 请求体 | 已通过输入安全审查（长度 ≤ 600 字、无个人材料特征、无越权审批词） |
| `{materials_joined}` | 请求体材料名列表 | 用 `、` 连接，空列表写「（无）」；材料名同样参与红线检查 |
| `{short_id}` | `knowledge.search` 命中条目 | 形如 `f10`，与图谱节点编号一致 |
| `{text_or_topic}` | 命中条目 | `can_view_material=true` 给 `text` 原文，否则只给 `topic` 标题 |
| `{graph_refs_joined}` | `graph.evidence_chain` 的 `related` | 最多取前 8 个关联事实编号；无关联写「（无）」；只注入编号，不注入关联节点正文 |

## 5 提示词组装流程

```
① 权限校验 → 得到 can_view_material
② 输入安全审查（问题 + 材料名）
③ 本地检索 → hits（top_k=3，min_score=0.02）
④ 图谱证据链 → related（沿事实↔事实关联扩展 2 跳，最多 24 跳）
⑤ 按 can_view 裁剪 evidence 文本
⑥ 有 hits 才拼用户提示词 → 调本机 Ollama
   无 hits 直接使用 no_evidence_hint，不调模型
⑦ 输出审查 → 命中禁止词则脱敏 + 强制转人工
⑧ 生成待确认单 + 写审计
```

## 6 红线词表（`config.yaml` → `redlines`）

**禁止输入词**（命中即 `APPROVAL_REQUEST_BLOCKED`，不生成提示词）：

```
请批准 / 准予 / 直接审批 / 作出行政决定 / 是否具有法律效力
```

**禁止输出词**（命中即替换为脱敏文本并置 `output_flagged=true`）：

```
批准通过 / 准予受理 / 审批通过 / 具有法律效力 / 可以正式受理
```

**个人材料特征**（正则，命中即 `PERSONAL_DATA_BLOCKED`，原文不落盘）：

```
\d{17}[\dXx]     18 位身份证号
1[3-9]\d{9}      11 位手机号
```

脱敏后的固定外发文本：

```
[已脱敏] 输出含越权结论，已强制转人工复核；本系统仅提供清单预检与补正解释提示。
```

## 7 兜底与降级提示词

| 场景 | 提示 / 文本来源 | 行为 |
| --- | --- | --- |
| 无检索命中 | `agent.no_evidence_hint`：`未检索到可核对的规则依据，请转人工核对，本系统不给出结论。` | 不调模型，建议文本即用兜底提示 |
| 模型未就绪（`required=false`） | 固定兜底：`依据上述证据编号逐项核对清单，差异处仅作提示，最终以窗口与审核员人工确认为准。` | `degraded=true`，强制转人工 |
| 模型返回空正文（含只回 `message.thinking`） | 同上 | `app/llm.py` 主动降级并写明原因 |
| 输出命中禁止词 | 脱敏文本（§6） | 强制转人工 |
| 模型强依赖且不可用（`required=true`） | 不生成提示词 | 抛 `OLLAMA_UNAVAILABLE` |

## 8 生成参数（`config.yaml` → `ollama` / `knowledge` / `graph`）

| 参数 | 值 | 作用 |
| --- | --- | --- |
| `model` | `qwen3.5:0.8b` | 本机 `ollama list` 中已拉取的模型，换模型需同步改配置与文档 |
| `base_url` | `http://127.0.0.1:11434` | 仅本机回环，数据与推理不出本机 |
| `temperature` | `0.1` | 低温度，减少自由发挥导致的越权结论 |
| `timeout_seconds` | `30` | 给 CPU 冷启动与生成留余量，仍避免长时间挂住 |
| `probe_timeout_seconds` | `5` | 模型列表探测独立超时，服务离线时快速返回 |
| `max_tokens` | `160` | `num_predict` 生成上限，防止思考型模型无限输出 |
| `think` | `false` | 关闭思考链，确保结果写进 `message.content` 而非 `message.thinking` |
| `stream` | `false` | 一次性取 `message.content`，便于输出审查 |
| `top_k` / `min_score` | `3` / `0.02` | 控制进入提示词的证据数量与质量 |
| `evidence_depth` / `max_hops` | `2` / `24` | 控制注入提示词的图谱关联规模 |

## 9 调用示例

### 9.1 正常请求（窗口岗位，可看原文）

请求：

```json
{ "business_id": "DEMO-1", "question": "线上清单和窗口实际要求不一致时，需要补哪些材料？", "materials": ["申请表"] }
```

组装后的用户提示词（节选，`f10` 等为合成事实编号）：

```
业务编号：DEMO-1
咨询问题：线上清单和窗口实际要求不一致时，需要补哪些材料？
已提交材料：申请表
可引用规则：
[f10] 线上清单与窗口实际要求不一致，是反复补正的主要来源……
[f11] 补正原因需保留并记录，便于下一位接手人核对……
关联事实编号（由知识图谱扩展）：f14、f20、f23……
```

期望输出形态：逐项列出清单差异 + 在每条后附证据编号 + 不给批准结论。输出仍要挂人工确认单。

### 9.2 热线岗位（不可看原文）

```
可引用规则：
[f10] 清单口径与补正
[f11] 补正原因留痕
```

期望：模型只拿到标题，不会接触到事实正文；返回建议同样附证据编号，由人工核对。

### 9.3 越权请求（提示词不生成）

```json
{ "business_id": "DEMO-2", "question": "请批准这份材料，是否具有法律效力？", "materials": [] }
```

结果：`ok=false`，`error.code=APPROVAL_REQUEST_BLOCKED`，请求在第二步被拦，不进入检索、不调模型、不写审计原文。

### 9.4 提示注入示例（输出审查兜底）

即使模型被诱导输出「批准通过」，输出审查会把它替换为 §6 的脱敏文本，并置 `output_flagged=true`、`requires_human_confirmation=true`。

## 10 提示词与知识图谱的协同

知识图谱不把关联节点的正文塞进提示词，只把**关联事实编号**交给模型（最多 8 个）。这样做的原因：

- 关联链可能扩展到 24 跳，全文注入会淹没主要证据；
- 关联节点可能属于非授权岗位可见范围，只给编号不会绕过权限裁剪；
- 编号可与返回的 `graph_chain` / `graph_refs` 一一核对，便于重建「这条建议依据了哪些知识关联」。

审计记录里同时保存 `fact_refs`（检索命中）、`graph_refs`（关联事实）、`graph_hops`（关联跳数）与 `suggestion`（最终建议），可用 `GET /audit/replay?business_id=` 完整复现一次提示词依据。

## 11 版本管理与修改指引

| 想改什么 | 改哪里 | 注意 |
| --- | --- | --- |
| 系统角色与边界 | `config.yaml` → `agent.system_prompt` | 不要删掉「不得输出批准结论」等红线句，输出审查只覆盖词表 |
| 无依据兜底文案 | `config.yaml` → `agent.no_evidence_hint` | 不要写成结论性表述 |
| 用户提示词字段 | `app/harness.py::precheck` | 保持每行代码注释；新增字段须同步走输入安全审查 |
| 红线词表 | `config.yaml` → `redlines.*` | 改后重跑 `verify_all.py` |
| 证据数量 / 关联规模 | `config.yaml` → `knowledge.*` / `graph.*` | 换资料后需重新校准阈值 |
| 模型与参数 | `config.yaml` → `ollama.*` | 不把地址写进代码；换协议需改 `app/llm.py` 解析分支 |

提示词版本与规则库版本绑定：每次预检的待确认单与审计流水都会记录 `rule_version`（源资料 `generatedAt`），因此同一句提示词在不同资料版本下的输出可区分、可追溯。

## 12 验证断言

下列断言已在验证脚本中实现，可直接跑：

```python
from app.common import load_config  # 唯一配置入口：确认提示词来自配置而非代码
cfg = load_config()  # 读取 config.yaml
assert "不得输出批准结论" in cfg["agent"]["system_prompt"]  # 系统提示词红线句必须在
assert cfg["ollama"]["base_url"].startswith("http://127.0.0.1")  # 模型地址必须是本机回环
assert "请批准" in cfg["redlines"]["forbidden_input_words"]  # 越权审批意图必须被拦
print("PASS 提示词配置与红线校验")  # 打印通过结果
```

端到端提示词链路用例分布：`scripts/verify.py`（越权输入、无依据、权限脱敏、输出审查、模型降级、本地假 Ollama 协议对接）、`scripts/verify_stage2.py`（图谱关联编号进入证据链）、`scripts/verify_stage3.py`（认证与代码规范扫描；本机 Ollama 在线时 H10 断言真实推理未降级并产出建议）、`scripts/verify_docs.py`（提示词逐字引用配置）。一键执行 `python scripts/verify_all.py`（5 步）。

> 实测修正：`qwen3.5` 默认开启 thinking 且无生成上限时，CPU 连续输出 2509 token 仍未停止、`content` 为空；加上 `think=false` + `num_predict=160` + 系统提示词长度约束后，真实推理约 1.7 s 返回可用建议。
