## 1 项目背景

云州市便民服务中心「办事材料预检与服务协同」现状为纯人工链路：线上清单与窗口实际要求不一致，群众按线上清单备齐材料后仍被窗口退回补正，形成「材料补了一次又一次」的反复跑。现场调研与业务挖掘材料给出的可核对口径为：补正率约 36%、清单解释约 12 分钟/次、每日约 600 件咨询、人工逐项核对约 8 人时/日；同时存在三套「办完」口径、便签说明不随单据交接、规则版本冲突、关键系统不可用等协同问题。

上述数字均为访谈口径，样本与时间窗待复核，本系统不作为已验证基线使用，只作为需求背景。现状流程图见同目录 `云州市便民服务中心-现状流程图.png`。

## 2 系统定位与边界

系统定位为**只读核对 + 人工交接的辅助智能体**，只做两件事：清单一致性预检、补正解释提示。

明确不做：

- 不输出批准结论、不判断能否受理、不解释真实法律效力；
- 不代替行政审批，不回写任何业务系统；
- 不导入真实个人材料，不使用云端模型或外部数据服务；
- AI 结论一律不直接生效，必须挂人工确认单，由接手岗位确认后才完成责任转移。

首期范围：两类非紧急事项、历史资料回放后小范围并行试点；一致率 99% 属验收目标，基准与裁定人待定，不在代码中写死。

### 3.2 非功能与代码约束

- 所有对外接口统一返回 `{"ok": bool, "data": ..., "error": {"code": str, "msg": str}}`；业务失败也返回 HTTP 200，由 `ok` 与 `error.code` 判定。
- 配置文件统一为 `config.yaml`；密钥、模型地址、模型名、端口、阈值、红线词表一律不写死在代码中。
- 每个函数写中文 docstring，说明入参、出参、失败时的行为；关键业务逻辑（安全审查、权限校验、人工确认、认证）写中文行内注释说明「为什么这么卡」；源码每行带注释。
- 不引入需求之外的框架或中间件：无数据库、无向量库、无图数据库、无消息队列、无缓存、无第三方 Agent 框架、无模型 SDK。

## 4 总体架构

分层如下，全部进程内调用，无跨服务通信：

```
对外接口层   app/main.py        FastAPI 路由、参数校验、统一响应、全局异常、认证依赖
运行壳层     app/harness.py     AgentHarness 八步编排（唯一业务入口）
关卡层       app/guards.py      安全审查 / 权限校验 / 输出审查
             app/auth.py        角色令牌绑定认证
             app/confirmation.py 待确认单与签核
能力层       app/knowledge.py   规则库构建与标准库检索
             app/graph.py       知识图谱构建、关联查询、多跳推理、原子落盘
             app/llm.py         本机 Ollama 调用与降级
基础层       app/common.py      配置加载、统一响应、JSON / JSONL 本地存储
数据层       kb/rules.json      36 条合成事实（规则库）
             kb/graph.json      知识图谱快照（节点 + 语义关联）
             data/*.json(l)     待确认单与审计流水
配置层       config.yaml        唯一配置入口
```

一次预检的数据流：

```
请求（X-Role / X-Actor / X-Agent-Token + 业务编号 / 问题 / 材料名）
  → 认证依赖 _gate（角色与令牌同源）
  → ① 权限校验 check_role → ② 安全审查 review_input
  → ③ 本地检索 knowledge.search（IDF 加权余弦，取 top_k 证据）
  → ④ 图谱证据链 graph.evidence_chain（沿事实↔事实关联多跳扩展）
  → ⑤ 取资料版本 rule_version
  → ⑥ 组装提示词 → 本机 Ollama /api/chat（未就绪则降级）
  → ⑦ 输出审查 review_output（越权结论脱敏）→ ⑧ 生成待确认单 + 写审计
  → 统一响应：建议 + 证据 + 关联链 + 待确认单 + 模型状态（requires_human_confirmation 恒为 True）
```

## 5 八步编排与三道卡点

| 步骤 | 动作 | 拦截原因（为什么这么卡） |
| --- | --- | --- |
| 1 | 权限校验 | 只有授权岗位能发起预检；无角色、伪造角色、越权动作一律拒绝，防止伪造请求头绕过权限矩阵 |
| 2 | 输入安全审查 | 真实个人材料、超长文本、要求系统作行政审批或解释法律效力的说法，全部拦在检索之前且不落盘原文 |
| 3 | 本地检索 | 只用合成资料；无命中即「无依据」，不调模型、不凭空生成 |
| 4 | 图谱证据链 | 从命中事实沿知识关联扩展到关联事实，让每条提示可回溯到证据链 |
| 5 | 资料版本 | 版本写入待确认单与审计，便于事后定位用的是哪一版规则 |
| 6 | 本机推理 | 仅当存在依据才调模型；按角色决定给模型看原文还是仅标题 |
| 7 | 输出安全审查 | 模型可能被提示注入诱导输出批准 / 受理 / 效力结论，命中即脱敏并强制转人工 |
| 8 | 人工确认 + 审计 | AI 只作提示，任何建议必须挂单据；接手人、确认时间、人工改动、签核人入审计才能重建处理链 |

人工确认门细化：禁止发起人自确认、单据 3600 秒超时作废、结论白名单 `accept / reject / revise`；写知识关联还额外要求单据已 `confirmed`、登记人必须是该单据签核人、业务编号一致、关系语义在白名单内、三元组不重复。

## 6 知识库设计

- **规则源**：仅 `../discovery-report.json` 的 `requirements[].evidence[]`，取 `id / text / source / character` 与需求标题，构建时按证据编号去重；命中身份证号、手机号等个人材料特征的条目只计数不入库（本次 `skipped=0`）。
- **规则库**：`kb/rules.json`，含 `rule_version`（源资料 `generatedAt`）、`count=36`、逐条 `id / short_id(f00–f55 形式) / topic / text / source / character`。
- **检索算法**：纯标准库实现。中文按单字 + 相邻二字切分，英文数字成词；词频经平滑 IDF 加权后计算余弦相关度；`min_score=0.02` 以下视为无依据，`top_k=3`。不依赖分词库或向量库，代价是长问句命中可能偏，需按资料调阈值。
- **权限脱敏**：`can_view_material=false` 的角色（热线、平台、主任）只拿到编号与标题，连提示词里都不塞原文。

## 7 知识图谱设计（知识与知识之间的关联）

### 7.1 节点与关联

| 类型 | 数量 | 说明 |
| --- | --- | --- |
| fact 事实 | 36 | 每条规则事实一个节点，正文放 `meta.text` 便于按权限裁剪 |
| topic 需求 | 6 | 需求标题 |
| role 岗位 | 6 | 访谈事实提出岗位 |
| source 资料 | 6 | 由 `source` 串末段提取的資料类型 |
| version 版本 | 1 | 当前资料版本 |

合计 **55 节点 / 535 条关联 / 11 类关系**。关联均为可核对依据，未编造冲突关系：

| 关系 | 条数 | 建边依据 |
| --- | --- | --- |
| 属于需求 / 包含事实 | 36 / 36 | 事实归属 `requirements` 分组及反向 |
| 由谁提出 / 涉及岗位 | 36 / 36 | `evidence.character` 及反向 |
| 出自资料 / 收录事实 | 36 / 36 | `evidence.source` 及反向 |
| 生效版本 / 版本收录 | 36 / 36 | 规则库版本及反向 |
| 同一需求共现 | 180 | 同需求内事实两两组合，正反向各一条 |
| 内容相关 | 54 | 正文中文二字词 Jaccard ≥ 0.08，每条事实最多 3 条，取相关度最高者，`note` 写明分值 |
| 援引 | 13 | 事实正文完整包含另一事实原文，直接援引关系 |

### 7.2 查询能力

| 能力 | 算法 | 关键参数 |
| --- | --- | --- |
| 关联查询 `relations` | 扫描关联表，出向 + 入向，按 `rel` 过滤 | `max_nodes=60` |
| 最短关联链 `shortest_path` | 广度优先 + 父指针回溯 | 只走事实↔事实关联 |
| 多跳子图 `subgraph` | 逐层 BFS，节点附跳数 | `max_depth=4`、`max_nodes=60`、`max_edges=120` |
| 证据链 `evidence_chain` | 多源 BFS，逐跳去重并按 (跳数, 关系) 排序 | `evidence_depth=2`、`max_hops=24` |
| 人工写关联 `add_link` | 三元组去重后原子落盘，重启自动回载 | `writable_relations` 六种白名单 |

> 早期版本允许沿全部双向边扩散，2 跳即覆盖全图（340 跳），证据链失去可核对性。现限定「只沿事实↔事实的关联扩散」并加条数上限，超限时返回 `truncated=true`，不得把截断结果当完整图。

## 8 本地模型接入（Ollama）

- 调用方式：标准库 `urllib.request` POST `http://127.0.0.1:11434/api/chat`，请求体 `model / stream:false / think:false / options.temperature / options.num_predict / messages`；解析 `message.content`。地址、模型名、超时、温度、生成上限与思考开关全部来自 `config.yaml`。
- 参数：本机已拉取 `qwen3.5:0.8b`（约 1 GB、CPU 推理）、`temperature=0.1`、`max_tokens=160`、`think=false`、`timeout_seconds=30`、`probe_timeout_seconds=5`。低温度减少自由发挥导致的越权结论。
- 实测修正：`qwen3.5` 属思考型模型，默认开启 thinking 时结果落在 `message.thinking`、`content` 为空，且没有生成上限时 CPU 连续输出 2509 token 仍未停止；因此请求显式关闭思考并设 `num_predict`，系统提示词追加「回答控制在 120 字内」。实测真实推理 `llm.generate` 约 1.7 s、完整 `precheck` 约 6 s，返回可用建议且 `degraded=false`。模型返回空正文时主动降级，不把空建议算作推理成功。
- 降级：`required=false` 时连接拒绝 / 超时 / HTTP 错误均返回 `degraded=true` 且 `text=""`，上层改用检索提示兜底，人工确认链路照常；`required=true` 时抛 `OLLAMA_UNAVAILABLE`。响应结构异常抛 `OLLAMA_BAD_RESPONSE`；模型返回空正文同样按降级处理。
- 自检：`scripts/check_ollama.py` 用独立的 `probe_timeout_seconds` 探测 `/api/tags`，退出码 0 就绪 / 1 服务未启动 / 2 在线但缺模型，只打印可操作命令，不自动下载模型。服务在线且模型匹配时，`verify_stage3.py` 的 H10 自动断言真实推理未降级并产出非空建议。
- 数据不出本机：服务绑定 `127.0.0.1`，提示词中不含请求原文之外的业务数据，非授权岗位连证据原文都不进入提示词。

提示词完整设计、模板、变量来源、红线词表、示例与版本管理见 **`docs/提示词.md`**。核心约定：系统提示词集中在 `config.yaml` 的 `agent.system_prompt`；用户提示词由 `AgentHarness.precheck` 按固定格式拼接，只注入业务编号、咨询问题、已提交材料名、检索证据（按权限裁剪）与图谱关联编号；输出必须引用证据编号，且必须再过一次输出安全审查。

## 10 安全、权限与数据红线

### 10.1 认证

`app/auth.py` 从环境变量 `AGENT_ROLE_TOKENS` 读取 `{"角色键":"令牌"}` JSON（每次请求重读，支持运行时轮换），用 `hmac.compare_digest` 做常量时间比较；校验角色是否在白名单、令牌是否签发、令牌归属角色是否与请求角色一致。错误码 `AUTH_NOT_CONFIGURED / AUTH_BAD_TOKENS / AUTH_TOKEN_DUPLICATED / AUTH_REQUIRED / AUTH_FAILED / AUTH_ROLE_MISMATCH / ROLE_REQUIRED / ROLE_UNKNOWN`。11 个业务路由统一挂 `Depends(_gate)`，`/health` 免凭据便于探活。凭据不落盘、不写进命令历史。

### 10.2 六角色权限矩阵

| 角色键 | 岗位 | 预检 | 查看材料原文 | 人工确认 |
| --- | --- | --- | --- | --- |
| `window` | 窗口工作人员 | 是 | 是 | 否 |
| `reviewer` | 业务审核员 | 是 | 是 | 是 |
| `supervisor` | 数据与流程监督员 | 是 | 是 | 是 |
| `hotline` | 热线服务负责人 | 是 | 否 | 否 |
| `platform` | 政务平台工程师 | 否 | 否 | 否 |
| `director` | 服务中心主任 | 否 | 否 | 否 |

### 10.3 数据红线

- 规则源仅合成训练资料；输入命中身份证 / 手机号等特征或超 600 字直接拒绝且不落盘原文。
- 禁止输入词：请批准、准予、直接审批、作出行政决定、是否具有法律效力。
- 禁止输出词：批准通过、准予受理、审批通过、具有法律效力、可以正式受理；命中即替换为脱敏提示并强制转人工。
- 审计保留业务编号、资料版本、事实引用、图谱关联、建议结果、人工改动、签核人；单行 JSONL 追加，可按业务编号回放重建处理链。

统一响应示例：

```json
{ "ok": true, "data": { "...": "..." }, "error": { "code": "OK", "msg": "" } }
```

```json
{ "ok": false, "data": null, "error": { "code": "AUTH_ROLE_MISMATCH", "msg": "凭据与请求角色不一致，禁止借用账号" } }
```

全局异常处理器把 `BizError`、`RequestValidationError`、`HTTPException`、未捕获异常统一改写为上述结构，HTTP 状态恒为 200，不回显堆栈与输入原文。

主要错误码：`CONFIG_*`、`AUTH_*`、`ROLE_*`、`ACTOR_REQUIRED`、`INPUT_TOO_LONG`、`PERSONAL_DATA_BLOCKED`、`APPROVAL_REQUEST_BLOCKED`、`KB_MISSING`、`SOURCE_*`、`GRAPH_*`（含 `GRAPH_CONFIRM_REQUIRED` / `GRAPH_SIGNER_MISMATCH` / `GRAPH_LINK_EXISTS`）、`TICKET_*`、`SELF_CONFIRM_BLOCKED`、`DECISION_INVALID`、`OLLAMA_*`、`STORE_READ_FAILED`、`ERR_VALIDATION / ERR_HTTP / ERR_INTERNAL`。

## 12 配置管理

`config.yaml` 为唯一配置入口，含 `service / auth / agent / ollama / knowledge / roles / redlines / confirmation / audit / graph` 十节。`load_config()` 用 `yaml.safe_load` 读取并校验必需节，缺节即抛 `CONFIG_INVALID`，绝不用代码内默认值补位；相对路径统一由 `resolve_path()` 挂到项目根目录。密钥（凭据表）走环境变量名 `AGENT_ROLE_TOKENS`，模型地址与名称走 `ollama` 节，均不出现在源码中。

## 16 已知风险与后续改进

1. **Ollama 服务需在新终端启动**（`ollama serve`）：模型权重 `qwen3.5:0.8b` 本机已拉取，代码不自动下载；服务在线时 `verify_all.py` 自动断言真实推理，离线时只覆盖降级路径并由本地假 Ollama 覆盖协议对接。会话关闭后服务可能退出，重跑验证前先启动。
2. **认证只在 HTTP 依赖层**：进程内直接调用 `AgentHarness` 仍免认证；凭据无过期、无轮换审计，`auth.required=false` 会退回明文模式。
3. **图谱快照优先回载**：改动 `discovery-report.json` 后必须重跑 `build_kb.py` + `build_graph.py`，否则关联仍是旧版本。
4. **业务失败也返回 HTTP 200**：调用方必须判断 `ok` 与 `error.code`，只看状态码会误判。
5. **本地 JSONL 审计**：写锁仅进程内有效，无留存期清理；多进程部署需换成带跨进程锁的存储。
6. **标准库中文检索**：`min_score / top_k / related_threshold / related_top_k` 为经验值，换资料后需重新校准。
7. **模型协议**：按 Ollama `/api/chat` 的 `message.content` 解析；若改用其他本地模型服务，只需改 `app/llm.py` 的解析分支。
8. **harness 释义**：按项目内自研运行壳实现；若课程指定具体仓库，替换接入层即可。
9. **小模型证据编号漂移**：0.8B 本地模型可能引用提示词未给出的证据编号；建议仅为提示，必须由接手人按返回的 `evidence_ids` 逐项核对后才生效，系统不自动采信。
10. **docx 由 md 转换生成**：改 `技术方案.md` 后需重建 `技术方案.docx`，`verify_docs.py` 的 D04 / D06 会在内容漂移时报错。
